Chapter 6 — Backend Architecture & Supabase Services
6.1 Purpose

This chapter defines the backend architecture for Co-op, detailing the use of Supabase as the cloud platform, the database structure, authentication, storage, serverless functions, AI integration, synchronization services, and backend security.

The backend is designed to complement Co-op's offline-first desktop architecture by providing secure cloud services for synchronization, authentication, AI, backups, and reporting.

6.2 Backend Design Goals

The backend architecture must achieve the following goals:

Secure cloud synchronization
Offline-first compatibility
High availability
Horizontal scalability
Strong security
Low latency
Minimal maintenance
Future multi-tenant support

6.11 Authorization

Version 1.0 supports a single business owner.

Future versions will introduce:

Admin
Manager
Employee
Accountant

Authorization is enforced through Row Level Security policies.

6.12 Row Level Security (RLS)

RLS is mandatory for all user data.

Rules:

Users can only access their own records.
Cross-company access is prohibited.
Every query is filtered by ownership.

Example policy:

user_id = auth.uid()

No table should be publicly accessible unless explicitly intended.

↓

6.18 Conflict Resolution

Conflicts occur when both local and cloud versions have changed.

Resolution strategy:

Compare timestamps
Detect conflicting fields
Apply merge rules where possible
Prompt the user only when automatic resolution is unsafe

A conflict log must be maintained for auditing.

6.19 Realtime Features

Supabase Realtime may be used for:

Sync status updates
Notification delivery
License changes

Core business functionality must not depend on realtime connectivity.

6.20 Backup Metadata

Cloud metadata includes:

Backup ID
User ID
Company ID
Timestamp
Version
Checksum

Actual backup files remain stored locally unless future cloud backup features are introduced.

6.21 API Design Principles

Backend APIs should be:

Stateless
Versioned
Idempotent where applicable
Fully authenticated
Strongly validated

Responses use a consistent structure.

Example:

{
  "success": true,
  "data": {},
  "error": null
}
6.22 Error Handling

Every backend operation should return structured errors.

Example:

{
  "success": false,
  "error": {
    "code": "AUTH_FAILED",
    "message": "Invalid email or password."
  }
}

Internal details should never be exposed to clients.

6.23 Logging

Backend logs include:

Authentication
AI requests
Synchronization
Storage operations
Errors
License activation
Edge Function execution

Sensitive values (passwords, tokens, API keys) must never appear in logs.

6.24 Security

Backend security measures include:

HTTPS only
JWT validation
Row Level Security
Rate limiting
Input validation
SQL injection prevention
Secure secret management
Signed storage URLs
Encrypted communication

Security is mandatory for every endpoint and function.

6.27 Monitoring

Operational metrics include:

Active users

Metrics should be reviewed regularly to maintain service quality.

6.28 Acceptance Criteria

The backend implementation is considered complete when:

Authentication functions correctly.
Cloud synchronization is reliable.
Row Level Security protects all user data.
AI requests are securely routed through Edge Functions.
Storage buckets enforce proper permissions.
Edge Functions perform within target latency.
Errors are standardized and logged.
All services operate securely over HTTPS.
Chapter Summary

This chapter defines Co-op's backend architecture using Supabase as the cloud platform. By combining PostgreSQL, Supabase Auth, Storage, Realtime, and Edge Functions with the OpenAI Responses API, the backend provides secure authentication, cloud synchronization, AI capabilities, and scalable infrastructure while preserving Co-op's offline-first desktop experience.
