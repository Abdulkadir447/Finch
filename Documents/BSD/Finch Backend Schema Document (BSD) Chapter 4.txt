Chapter 4 — User Management Schema
4.1 Purpose

This chapter defines the User Management architecture for Finch. While Chapter 3 focused on authentication and identity verification, this chapter describes how authenticated users are represented within the application, how they interact with businesses, devices, preferences, permissions, and future organizational roles.

The User Management system is designed to support both Version 1 (primarily business owners) and future enterprise deployments with multiple users, departments, and role-based access control (RBAC).

4.2 Objectives

The User Management system must:

Store extended user information beyond authentication.
Support multiple businesses per account.
Prepare for multiple users per business.
Maintain user preferences and personalization.
Track user devices and sessions.
Record user activity.
Support future roles and permissions.
Integrate with audit logging and security.
Scale without schema redesign.

4.4 Core Tables

The User Management module consists of the following tables:

Table	Purpose
profiles	User profile information
user_businesses	Business memberships
user_roles	Role assignments
user_preferences	Personal settings
user_devices	Registered devices
user_sessions	Session history
user_activity	Activity timeline

Each table is described in later sections.

4.5 Profiles Table
Table: profiles

Stores personal information for every authenticated user.

Column	Type	Description
id	UUID	Primary key (Supabase Auth ID)
full_name	TEXT	Full legal or preferred name
email	TEXT	Primary email
avatar_url	TEXT	Profile image
phone_number	TEXT	Optional phone number
preferred_language	TEXT	Language preference
timezone	TEXT	Preferred timezone
created_at	TIMESTAMPTZ	Creation timestamp
updated_at	TIMESTAMPTZ	Last update timestamp

A profile exists for every authenticated account.

4.6 User–Business Relationship

A single user may belong to multiple businesses.

Likewise, a business may contain multiple users.

Relationship:

User
 │
 ├── Business A
 ├── Business B
 └── Business C

This many-to-many relationship is managed through the user_businesses table.

4.7 User Businesses Table
Table: user_businesses
Column	Type	Description
id	UUID	Primary key
user_id	UUID	References profiles.id
business_id	UUID	References businesses.id
role_id	UUID	References roles.id
joined_at	TIMESTAMPTZ	Date joined
is_default	BOOLEAN	Default business on login
created_at	TIMESTAMPTZ	Creation time

This table enables users to switch between businesses without signing out.

Although Version 1 focuses on business owners, Finch is designed for future role expansion.

Planned roles include:

Owner
Administrator
Manager
Accountant

Inventory Manager

Customer Support

Roles determine permissions but are managed separately from authentication.

4.10 User Preferences Table
Table: user_preferences

Stores personalized application settings.

Column	Type	Description
id	UUID	Primary key
user_id	UUID	User reference
theme	TEXT	Light, Dark, System
accent_color	TEXT	Selected accent color
language	TEXT	Preferred language
dashboard_layout	JSONB	Widget arrangement
notification_settings	JSONB	Notification preferences
keyboard_shortcuts	JSONB	Custom shortcuts
created_at	TIMESTAMPTZ	Creation time
updated_at	TIMESTAMPTZ	Last update

Flexible preferences are stored using JSONB where appropriate.

4.11 User Devices Table
Table: user_devices

Tracks devices used to access Finch.

Column	Type	Description
id	UUID	Primary key
user_id	UUID	User reference
device_name	TEXT	Computer name
operating_system	TEXT	Windows version
app_version	TEXT	Installed Finch version
last_login	TIMESTAMPTZ	Last successful login
trusted	BOOLEAN	Trusted device
created_at	TIMESTAMPTZ	Registration time

Future versions may allow users to revoke trusted devices remotely.

4.12 User Sessions Table
Table: user_sessions

Maintains session history.

Column	Type	Description
id	UUID	Primary key
user_id	UUID	User reference
device_id	UUID	Registered device
login_time	TIMESTAMPTZ	Session start
logout_time	TIMESTAMPTZ	Session end
ip_address	TEXT	Last known IP (cloud sessions)
status	TEXT	Active, Expired, Revoked

This table supports security auditing and session management.

4.17 Data Privacy

User management must comply with privacy best practices.

Sensitive information:

Passwords
Tokens
API keys

must never be stored within the User Management schema.

Only Supabase Authentication manages credentials.

4.18 Security Policies

Every user-related table must enforce:

Row Level Security (RLS)
Ownership validation
Business membership checks
Permission verification
Audit logging

No user may view or modify another user's information without authorization.

4.20 Performance Considerations

User-related queries should be optimized using indexes on:

user_id
business_id
email
last_login
role_id

Frequently accessed user preferences should be cached locally to reduce cloud requests.

4.21 Developer Implementation Notes

Implementation guidelines:

Keep authentication and user profile data logically separate.
Use UUIDs consistently across all user-related tables.
Cache user preferences locally for faster startup.
Record significant user actions in the activity log.
Design the schema to support future RBAC without structural changes.
Ensure all user tables enforce RLS and business isolation.
Avoid storing authentication secrets outside Supabase Auth.
4.22 Acceptance Criteria

The User Management Schema is complete when:

Every authenticated user has a profile.
Users can belong to multiple businesses.
Default business selection works correctly.
Preferences are stored and synchronized.
Devices and sessions are tracked.
User activity is recorded.
Future RBAC is supported.
RLS protects all user data.
Performance targets for user queries are met.
4.23 Chapter Summary

The User Management Schema extends Finch's authentication system by managing user profiles, business memberships, preferences, devices, sessions, and activity history. Its modular design supports the current owner-focused workflow while providing a scalable foundation for future multi-user organizations, role-based permissions, and enterprise collaboration. By separating identity, preferences, and business context, the system remains secure, maintainable, and ready for long-term growth.
