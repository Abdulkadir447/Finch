Chapter 1 — Backend Architecture & System Overview
1.1 Purpose

This document defines the complete backend architecture for Finch. It serves as the technical blueprint for developers responsible for implementing, maintaining, and scaling the backend infrastructure.

The backend is designed around five core principles:

Offline First
Security by Design
Scalability
High Performance
Future Expandability

Unlike traditional cloud-first applications, Finch prioritizes the local desktop experience while using the cloud for synchronization, backup, authentication, collaboration, and AI services.

1.2 Goals

The backend architecture must:

Support offline business operations.
Synchronize data reliably with the cloud.
Handle multiple businesses per account.
Support future multi-user organizations.
Protect customer and business data.
Scale from a single small business to enterprise deployments.
Provide reliable AI integration.
Minimize cloud bandwidth.
Support future mobile and web clients.

1.6 Backend Design Principles

Every backend component follows these principles.

Offline First

Every write operation is saved locally before synchronization.

Event Driven

Changes generate events instead of directly updating cloud resources.

Example:

Order Created

↓

Queue Event

↓

Sync Service

↓

Cloud Update
Modular

Every business domain is isolated.

Examples:

Orders
Inventory
Customers
Reports
AI

Each module has its own services and database schema.

Stateless Services

Cloud services should never depend on in-memory state.

Every request contains enough information to complete independently.

Future Ready

The architecture supports:

Mobile applications
Web dashboard
Enterprise edition
Plugins
Public API

without requiring database redesign.

1.7 Multi-Business Architecture

A single account may own multiple businesses.

Example

John Doe

│

├── Grocery Store

├── Pharmacy

├── Restaurant

└── Electronics Shop

Every business is isolated.

Data from one business cannot access another unless explicitly authorized.

1.17 Recommended Enterprise Features

The following architectural features are part of Finch's backend from the beginning:

UUID primary keys for all major entities.
Row Level Security (RLS) on every business table.
Automatic created_at, updated_at, and deleted_at timestamps.
Database triggers for timestamp updates and audit logging.
Materialized views for high-performance dashboard analytics.
Background jobs for report generation, AI summarization, notification cleanup, and permanent deletion of expired soft-deleted records.
Optimistic concurrency using record versioning to reduce synchronization conflicts.
Session-based report caching that regenerates reports only after the application has been completely closed and reopened.
Dedicated synchronization queue to coordinate reliable offline-first data synchronization between SQLite and Supabase.
1.18 Success Criteria

The backend architecture is considered successful when:

Users can work completely offline.
Cloud synchronization is reliable and conflict-aware.
Multiple businesses are fully isolated.
Future multi-user roles are supported without redesign.
AI services integrate securely and efficiently.
Sensitive business data is protected by layered security.
The system scales without major architectural changes.
Performance remains consistent as datasets grow.
All backend services are modular, maintainable, and testable.
1.19 Chapter Summary

This chapter establishes the architectural foundation for Finch's backend. It defines the overall system structure, technology stack, design philosophy, security model, synchronization approach, and scalability goals. By adopting an offline-first, modular, and multi-tenant architecture backed by SQLite and Supabase, Finch is prepared to support current business needs while remaining flexible enough for future features such as enterprise collaboration, mobile clients, and advanced AI capabilities.
