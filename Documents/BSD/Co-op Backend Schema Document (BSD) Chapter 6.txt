Chapter 6 — Roles & Permissions Schema
6.1 Purpose

This chapter defines Co-op's Role-Based Access Control (RBAC) architecture. Although Version 1 primarily targets business owners, the backend is designed from the beginning to support multiple users with different responsibilities, ensuring secure access to business resources.

The RBAC system separates authentication (who a user is) from authorization (what a user can do), allowing the application to grow into a collaborative, enterprise-ready platform without requiring database redesign.

6.2 Objectives

The Roles & Permissions system must:

Support multiple users per business.
Provide fine-grained permission control.
Support default system roles.
Support custom roles in future versions.
Enforce least-privilege access.
Integrate with Row Level Security (RLS).
Log permission changes.
Scale to enterprise organizations.

6.4 RBAC Principles

Co-op follows these security principles:

Least Privilege
Explicit Permissions
Business Isolation
Role Separation
Auditability
Future Expandability

No user receives permissions they have not been explicitly granted.

6.6 Roles Table
Table: roles

Stores available roles.

Column	Type	Description
id	UUID	Primary key
business_id	UUID	NULL for system roles
role_name	TEXT	Role name
description	TEXT	Role description
is_system	BOOLEAN	Built-in role
created_by	UUID	User who created the role
created_at	TIMESTAMPTZ	Creation timestamp
updated_at	TIMESTAMPTZ	Last update

System roles are shared across businesses, while future custom roles belong to individual businesses.

6.7 Permissions Table
Table: permissions

Defines every permission available in Co-op.

Column	Type	Description
id	UUID	Primary key
permission_key	TEXT	Unique permission identifier
module	TEXT	Related module
description	TEXT	Human-readable description
created_at	TIMESTAMPTZ	Creation timestamp

Example permission keys:

orders.create

orders.read

orders.update

orders.delete

inventory.read

inventory.update

customers.create

reports.generate

ai.use

settings.manage

Permissions use a consistent module.action format.

6.8 Role Permissions Table
Table: role_permissions

Maps roles to permissions.

Column	Type	Description
id	UUID	Primary key
role_id	UUID	References roles.id
permission_id	UUID	References permissions.id
created_at	TIMESTAMPTZ	Assignment timestamp

This many-to-many relationship allows flexible permission management.

6.12 Default System Roles
Role	Description
Owner	Full unrestricted access
Administrator	Business administration without ownership
Manager	Operational management
Accountant	Financial access
Inventory Manager	Inventory management
Sales Representative	Sales and customer management
Cashier	Sales processing only
Support Staff	Limited operational access

These roles provide sensible defaults while allowing future customization.

Businesses will eventually be able to create custom roles.

Example:

Warehouse Supervisor

Marketing Manager

6.14 Permission Inheritance

System roles have predefined permission sets.

Example:

Owner

↓

All Permissions

Administrator

↓

Most Permissions

Cashier

↓

Custom roles do not automatically inherit permissions; they receive only those explicitly assigned.

6.15 Row Level Security Integration

Authorization is reinforced using PostgreSQL RLS.

Every request validates:

Authenticated user
Business membership
Role assignment
Permission check
Resource ownership (when applicable)

RLS acts as the final enforcement layer.

6.16 Audit Logging

The following events are recorded:

Role assigned
Role changed
Role removed
Permission granted
Permission revoked
Unauthorized access attempt

These events support security investigations and compliance.

6.17 Future Department Support

The RBAC system is designed to support organizational departments.

Example:

Business
 │
 ├── Sales
 ├── Finance
 ├── Inventory
 ├── Operations
 └── Administration

Departments may later be linked to roles and reporting structures.

6.18 Emergency Access

Only the business owner can:

Delete the business.
Transfer ownership.
Manage licenses.
Assign or revoke owner privileges.
Restore archived businesses.

These actions cannot be delegated unless explicitly supported in future releases.

6.19 Performance Considerations

Indexes should exist on:

role_id
permission_id
user_id
business_id

Permission checks should be cached for the duration of the active session to minimize database lookups.

6.20 Developer Implementation Notes

Implementation guidelines:

Use UUIDs for all RBAC tables.
Define permissions using the module.action naming convention.
Keep authentication and authorization as separate concerns.
Store role assignments in user_businesses.
Cache resolved permissions during a user's active session.
Enforce authorization both in application logic and with PostgreSQL RLS.
Log every permission-related change to the audit system.
6.21 Acceptance Criteria

The Roles & Permissions Schema is complete when:

Users can be assigned roles per business.
Roles map correctly to permissions.
Authorization checks occur before protected operations.
System roles function correctly.
Future custom roles are supported.
RLS enforces access restrictions.
Permission changes are audited.
Session-based permission caching improves performance.
Business owners retain exclusive access to critical administrative functions.
6.22 Chapter Summary

The Roles & Permissions Schema provides Co-op with a secure, scalable authorization framework built on Role-Based Access Control (RBAC). By separating identity from permissions, supporting business-specific role assignments, integrating with PostgreSQL Row Level Security, and preparing for custom roles and departments, the system is ready to evolve from a single-owner desktop application into a collaborative, enterprise-grade business platform while maintaining strict security and data isolation.
