Chapter 15 — Synchronization & Offline Schema
15.1 Purpose

The Synchronization & Offline module is one of the core architectural pillars of Co-op. It enables users to continue working without an internet connection while ensuring that all data is synchronized efficiently and securely once connectivity is restored.

Co-op follows an Offline-First architecture, where the local SQLite database is the primary working database and Supabase PostgreSQL serves as the cloud synchronization and backup layer.

This design ensures high performance, reliability, and uninterrupted business operations regardless of network availability.

15.2 Objectives

The Synchronization module must:

Support full offline functionality.
Synchronize only modified records.
Maintain data consistency.
Resolve synchronization conflicts safely.
Queue offline operations.
Restore interrupted sessions.
Compress synchronization payloads.
Support automatic background synchronization.
Minimize bandwidth usage.
Scale to future multi-device collaboration.

15.9 Conflict Detection

Conflicts occur when:

Local Version

≠

Cloud Version

Examples:

Same order edited on two devices.
Product updated simultaneously.
Customer modified from multiple locations.
15.10 Conflict Resolution

Based on your application flow decisions, Co-op uses a user-selectable strategy, with Ask User as the default.

Supported strategies:

Ask User (default)
Local Version Wins
Cloud Version Wins

When a conflict is detected, the user is shown both versions and asked which one to keep.

15.12 Incremental Synchronization

Instead of uploading the entire database, Co-op synchronizes only changed records.

SQLite

↓

Modified Records

↓

Compressed Payload

↓

Supabase

This significantly reduces bandwidth and improves speed.

15.13 Compression

Following your requirements, synchronization files are kept very small.

Methods include:

Uploading only changed fields where possible.
Compressing payloads before transmission.
Batching related operations.
Removing redundant metadata.

This minimizes network usage without affecting reliability.

15.14 Deleted Records
Table: deleted_records

Soft-deleted records are tracked until all devices acknowledge the deletion.

Fields:

Table Name
Record ID
Deleted At
Deleted By
Sync Status

Once synchronized and past the retention period, records are permanently removed.

15.15 Background Synchronization

Synchronization runs automatically:

At application startup.
At configurable intervals.
After significant transactions.
Before application shutdown (when possible).
When connectivity is restored.

Users may also trigger manual synchronization.

15.16 Session Restoration

As specified in your application flow:

Co-op automatically restores the previous session after reopening the application.
If the application or computer is shut down completely, a new secure session token is generated.
Users only need to sign in once unless the session expires or security policies require re-authentication.

15.23 Developer Implementation Notes

Implementation guidelines:

Use SQLite as the authoritative local working database.
Use Supabase PostgreSQL as the cloud synchronization database.
Include a version field on all synchronized tables.
Maintain a persistent synchronization queue.
Compress synchronization payloads before upload.
Implement user-selectable conflict resolution, defaulting to "Ask User."
Store synchronization metadata separately from business data.
Restore the previous session automatically on startup.
Protect all synchronization endpoints with JWT authentication and RLS.
15.24 Acceptance Criteria

The Synchronization & Offline Schema is complete when:

The application functions fully offline.
All changes are written to SQLite immediately.
Only modified records are synchronized.
Synchronization payloads remain compact.
Conflicts are detected using version tracking.
Users can choose how conflicts are resolved.
Background synchronization operates automatically.
Previous sessions are restored after reopening the application.
Deleted records are synchronized correctly.
All synchronization operations are secure, audited, and recover gracefully from failures.
15.25 Chapter Summary

The Synchronization & Offline Schema establishes Co-op as a true offline-first business platform. By treating SQLite as the primary working database, maintaining a robust synchronization queue, tracking record versions, supporting intelligent conflict resolution, and synchronizing only incremental changes, the system delivers fast, reliable, and bandwidth-efficient performance. Combined with automatic session restoration, secure synchronization, and comprehensive auditing, this architecture provides a strong foundation for future multi-device collaboration and enterprise-scale deployments.
