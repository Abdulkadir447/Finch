Chapter 2 — Database Design Principles & Naming Standards
2.1 Purpose

This chapter defines the database standards, conventions, and architectural principles that every table, view, function, trigger, and API within Co-op must follow.

These standards ensure that the database remains:

Consistent
Scalable
Easy to maintain
Secure
Performant
Future-proof

Every developer working on Co-op must follow these guidelines.

2.2 Database Philosophy

Co-op follows five fundamental database principles:

1. Offline First

Every write operation begins in the local SQLite database before synchronizing to Supabase PostgreSQL.

2. Business Isolation

Every piece of business data belongs to exactly one registered business.

No business should ever access another business's data unless explicitly authorized in future enterprise editions.

3. Security by Default

Every table containing business data is protected using:

Row Level Security (RLS)
Authentication
Authorization
Secure API access
4. Modular Design

Each business module owns its own tables.

Example:

Orders
Inventory
Customers
Reports
AI
Notifications

Modules should remain loosely coupled while sharing common identifiers.

5. Scalability

The database should support:

One business
Thousands of businesses
Millions of records
Future enterprise deployments

without requiring redesign.

2.5 Primary Key Strategy

Every major table uses UUIDs.

Example

id UUID PRIMARY KEY

Reasons:

Better synchronization
Safer offline creation
Globally unique identifiers
Easier merging
Better future scalability

Auto-incrementing IDs should not be used for primary keys.

2.6 Foreign Key Strategy

Relationships use UUID foreign keys.

Example

order_id

customer_id

business_id

supplier_id

user_id

Foreign keys enforce referential integrity while maintaining flexibility.

2.11 Reserved Columns

The following column names have predefined meanings across the entire database.

Column	Purpose
id	Primary Key
business_id	Business ownership
created_at	Creation time
updated_at	Last update
deleted_at	Soft delete timestamp
created_by	User who created the record
updated_by	User who last modified the record
version	Record version
is_active	Active/inactive state

Developers should not repurpose these names.

JSONB is reserved for flexible or semi-structured data.

Examples:

Dashboard layouts
User preferences
AI metadata
Notification payloads
Import settings

Core business entities should use normalized relational tables instead of JSON.

2.20 Database Migrations

All schema changes are version-controlled through migrations.

Migration rules:

Never modify production tables manually.
Every schema change requires a migration script.
Migrations must be reversible where practical.
Database version must align with the application version.

2.23 Developer Implementation Notes

Implementation guidelines:

Use UUIDs for all primary keys and foreign key references.
Apply consistent snake_case naming across all database objects.
Enforce business isolation using business_id and RLS.
Include standard audit fields (created_at, updated_at, deleted_at, etc.) in all business tables.
Create indexes only where they provide measurable performance benefits.
Keep schemas normalized while using JSONB only for flexible metadata.
Review migrations in code review to maintain consistency and prevent breaking changes.
2.24 Acceptance Criteria

The database design standards are complete when:

All tables follow the naming conventions.
UUIDs are used consistently.
Standard audit fields exist across business tables.
Soft delete is implemented uniformly.
Business isolation is enforced.
Appropriate indexes and constraints are defined.
Migrations are version-controlled.
Documentation exists for all major database objects.
The schema supports offline synchronization and future scalability.
2.25 Chapter Summary

This chapter establishes the standards that govern Co-op's database design. By enforcing consistent naming conventions, UUID-based identifiers, standardized audit fields, business isolation, soft deletion, indexing strategies, and migration practices, the database becomes easier to maintain, more secure, and capable of supporting long-term growth. These principles form the foundation for every schema defined in the chapters that follow.
